# Technical Plan — Database Schema and Migrations (v1)

**Feature:** `database-schema-and-migrations` · **Version:** v1 · **Product item:** BP-002
**Branch:** `feature/bp-002-bp-003-bp-006-bp-031` (shared) · **Base:** `main`

## 1. Approach

The tenancy half of the schema is already shipped and migrated. This plan adds the **clinical half**
in one additive migration, keeps the in-memory test double in step with it, and produces the demo
dataset the later waves need. Three decisions shape it:

1. **One migration, additive only.** `Patient`, `Doctor` and `Appointment` land together because they
   reference each other; splitting them would mean three migrations with no value. The migration is
   pure DDL — `CREATE TABLE`, `CREATE INDEX`, foreign keys — with no `DROP`, no `TRUNCATE` and no
   rewrite of an existing table, which is what makes AC-003 provable on a populated database.
2. **The test double is part of the change.** `server/src/database/memory-prisma.ts` backs the
   in-memory path the API tests use. Adding models to `schema.prisma` without teaching the double
   leaves the suite unable to construct a patient or appointment, so T1.4 is not optional cleanup.
3. **The seed is deterministic and idempotent, with no new dependency.** A small seeded PRNG plus
   upserts on natural keys gives AC-006 and AC-007 without adding a faker package, and it keeps the
   generated data stable enough to assert against.

## 3. Data model

**Entities created**

| Entity        | Key fields                                                                                                              | Relations                                                                |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `Patient`     | `id`, `clinicId`, `firstName`, `lastName`, `dateOfBirth`, `phone`, `email?`, `gender?`, `createdAt`, `updatedAt`        | `clinic` → `Clinic` (restrict on delete, EC-005); `appointments`         |
| `Doctor`      | `id`, `clinicId`, `userId?`, `specialty`, `licenseNumber?`, `consultationMinutes`, `isActive`, `createdAt`, `updatedAt` | `clinic` → `Clinic`; `user` → `User` (`SetNull`, EC-004); `appointments` |
| `Appointment` | `id`, `clinicId`, `patientId`, `doctorId`, `startsAt`, `endsAt`, `status`, `reason?`, `createdAt`, `updatedAt`          | `clinic`, `patient` (cascade with the patient), `doctor`                 |

`AppointmentStatus`: `SCHEDULED`, `CONFIRMED`, `CHECKED_IN`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`,
`NO_SHOW`. The transitions between them are BP-019's, not this feature's.

**Indexes created:** `Appointment(doctorId, startsAt)` — a doctor's day; `Appointment(patientId)` — a
patient's history. `clinicId` is indexed implicitly by the foreign key on each table.

**Flow:** `prisma migrate deploy` creates the tables → the seed upserts 3 clinics, 10 doctors,
200 patients and 600 appointments → BP-015…BP-019 query them through Prisma.

## 4. API contracts

None. This feature adds no endpoint and changes no request or response shape; the tables are consumed
by later features, not exposed by this one.

## 5. Security

- **NFR-004 / CON-516:** every clinical table carries `clinicId` with a foreign key to `Clinic`, so a
  query that forgets the tenant filter cannot even join across clinics silently — it returns nothing
  without an explicit `where`. The migration contains only static DDL; all data access goes through
  Prisma's parameterised client, and no raw SQL is introduced.
- **NFR-003 / CON-519:** the seed reads `DATABASE_URL` from the environment (never a literal) and
  refuses to run when `NODE_ENV=production`, so a development fixture cannot be applied to a deployed
  database.
- **CON-506:** every seeded person is fictional — fixed fictional name list, `@riaya.local` and
  `example.org` addresses — and the seed header restates that these are local-only fixtures.
- The remaining CON-51x controls are NOT APPLICABLE with their rationale recorded in `spec.md` §6,
  because this feature adds no HTTP surface and no authentication path.

## 6. Performance

- **NFR-001:** the migration is small DDL on three new tables plus two indexes, so `migrate deploy` on
  an empty database is a few hundred milliseconds; the 60-second budget exists to cover CI cold
  starts, not the work itself.
- **NFR-003:** the seed writes 813 rows in sequential upserts inside a single transaction, which keeps
  it well inside the 60-second budget and leaves no partial state.
- The two indexes are the performance deliverable of this feature: they turn _a doctor's day_ and
  _a patient's history_ into index range scans rather than sequential scans of `Appointment`.

## 8. Risks

| Risk                                                                               | Mitigation                                                                                                   |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| The generated migration contains an unexpected destructive statement.              | T1.2 reads the emitted SQL before it is committed; `DROP`/`TRUNCATE` is a stop condition, not a review note. |
| The in-memory double drifts from `schema.prisma` and tests pass against a fiction. | T1.4 adds the same three models to the double in the same change.                                            |
| The seed doubles rows on a second run.                                             | Upsert on a natural key per entity; T3.2 runs it twice and compares counts.                                  |
| The seed runs against a non-development database.                                  | `NODE_ENV` guard (T2.2) — it refuses rather than warns.                                                      |
| A future feature makes `endsAt > startsAt` enforceable and forgets this gap.       | EC-003 records the gap and names BP-019 as the owner.                                                        |
